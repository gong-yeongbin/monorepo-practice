# 맥락 메모 — view_code 디코드 저장 (2026-09-04)

## 배경

`viewCodeCodec.encode`는 AES 암호문을 base64로 만든 뒤 `encodeURIComponent`를 씌운다(`138810c`, 2025-11-05 최초 구현부터).
트래킹 URL이 템플릿 문자열 치환으로 조립되고 별도 인코딩 단계가 없어, base64의 `+`·`/`·`=`를 URL에 안전하게 싣기 위한 조치였다.
그런데 이 인코딩된 문자열이 그대로 `daily_report`의 키가 됐고, 포스트백 매퍼는 Express가 디코드한 값을 다시 `encodeURIComponent`해 형식을 맞추고 있었다.

## 결정

- **URL에만 인코딩, DB에는 원문.** `encode()`와 트래킹 URL 조립은 손대지 않는다. 저장 직전 지점(트래킹 consumer, 포스트백 매퍼)에서만 `decodeURIComponent`한다.
- **디코드 지점은 트래킹 consumer.** use-case가 스트림에 보내기 전이 아니라 consumer가 저장하기 전에 디코드해, 배포 시점에 스트림에 남아 있던 인코딩된 메시지도 새 형식으로 저장된다.
- **포스트백은 매퍼에서 디코드.** 트래커는 클릭 당시 받은 인코딩된 view_code를 며칠 뒤 포스트백으로 되돌려 준다(귀속 기간). 트래커가 이를 URL 인코딩해 보내면 Express 디코드 후 `%2F`가 남으므로, 매퍼의 `decodeURIComponent`가 옛 클릭의 포스트백을 새 형식으로 정규화한다. 새 클릭(`%` 없음)에는 no-op.
- **`normalizeViewCode`는 잘못된 `%`에서 던지지 않는다.** 포스트백 엔드포인트는 공개 엔드포인트라 트래커가 보낸 이상값으로 500이 나면 안 된다. `decode()`가 실패 시 입력을 돌려주는 것과 같은 방침.
- **기존 행은 실행 당일(KST)만 변환한다(사용자 결정).** 지난 날짜는 두 테이블 모두 인코딩 형태라 서로 맞고(일자별 상세 → 인스톨 로그 조회도 같은 형식끼리 매칭), 배포 후 들어오는 포스트백은 당일 daily_report 행에만 집계되므로 당일 행만 새 형식과 맞추면 된다. 날짜를 박지 않고 `now()` 기준으로 잡아 배포일이 밀려도 맞다. 데이터는 1만 건 남짓이라 전체 변환도 1초 미만이지만, 사용자가 당일만 원했다. base64 문자 중 `encodeURIComponent`가 바꾸는 건 `/`·`+`·`=` 세 개뿐이라 `%2F`·`%2B`·`%3D` replace로 정확히 복원된다. 소문자 hex는 확인하지 못했고 비용이 없어 대소문자 무시(`gi`)로 처리한다.
- **지난 날짜 행은 인코딩 형태로 남는다.** 화면·엑셀에서 옛 날짜의 VIEW CODE는 `%2F` 형태, 당일 이후는 `/` 형태로 보인다.
- **unique 충돌 없음.** 새 코드가 원문 행을 쓰기 전에 마이그레이션이 먼저 돌므로(배포 순서) 당일 `(view_code, created_date)`에 두 형식이 공존하지 않는다.

## 부수 효과

- 매체 포스트백 URL(`buildMediaPostbackUrl`)은 **매체가 받는 값을 기존과 동일하게 유지한다**(사용자 결정). 저장값이 원문으로 바뀌었으므로 view_code만 먼저 `encodeURIComponent`해 인코딩된 형태로 만든 뒤 치환 인코딩을 태운다. URL상 `%252F`, 매체가 디코드하면 `%2F` 형태로 이전과 같다.
- 어드민 화면·엑셀의 VIEW CODE 컬럼에 `/`·`+`가 그대로 보인다.
- 프론트가 인스톨·이벤트 로그 조회 시 view_code를 `encodeURIComponent`하는 것은 여전히 필요하다(`+`가 그대로 가면 서버에서 공백이 된다). 주석만 실제 이유로 고쳤다.
