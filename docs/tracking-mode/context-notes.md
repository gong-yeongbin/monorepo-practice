# 맥락 메모 — 트래킹 차단 모드

작업 중 내린 결정과 그 이유를 기록한다. 계속 덧붙인다.

## 2026-09-07 — 설계 결정

### 503 을 쓴다 (500 이 아니라)

처음 요청은 "500 을 낼 수 있냐" 였으나 목적이 점검·긴급 차단으로 확인되어 503 으로 정했다.
500 은 "서버가 고장났다" 는 뜻이라 트래커·매체 쪽 재시도를 유발하고 모니터링 알람이 계속 울린다.
503 은 "일시적이고 곧 돌아온다" 를 뜻해 의도와 맞는다.

### 모드 값은 숫자가 아니라 이름

사용자가 처음 제안한 배치는 `0 = 정상, 1 = 1/2 확률, 2 = 전면 차단` 이었다.
숫자와 의미 사이에 규칙이 없어 매번 표를 봐야 하고, 긴급 상황에 반대로 넣을 위험이 있다.
또 값이 비었거나 파싱에 실패해 0 이 되는 경우와 "정상" 이 구분되지 않는다.
`open`/`half`/`closed` 로 정했다. 필요한 상태가 셋뿐이라 이름이 숫자보다 안전하다.

나중에 비율을 세밀하게 조절해야 하면 `pass_rate`(0~100 퍼센트) 형태로 넓히면 된다.

### 확률 방식 — 어뷰징 방어로는 한계가 있음을 알고 채택

사용자가 밝힌 목적은 "악의적 요청 차단" 이다. 확률 차단이 이 목적에 맞지 않는다는 점은 사전에 전달했다.

- 봇은 503 을 받으면 재시도한다. 2 번이면 75%, 3 번이면 87.5% 가 통과한다.
- 정상 사용자는 브라우저 top-level 리다이렉트라 재시도하지 않는다. 정상 클릭의 절반이 그대로 유실된다.

즉 봇은 거의 못 막고 실제 사용자만 막는 역방향 필터다.
사용자가 한계를 인지한 상태에서 확률 방식을 선택해 그대로 구현한다.

**어뷰징 방어가 실제 목표라면** 대안은 Valkey 기반 IP rate limit 이다.
`tracking.controller.ts` 주석과 `modules/CLAUDE.md` 에 이미 그 방향이 남아 있다
(기본 인메모리 저장소는 IP 키를 지우지 않아 이 경로에서 메모리·CPU 를 무한히 먹으므로 공유 저장소가 필요하다).
이번 스위치 구조를 그대로 두고 판정만 rate limit 으로 바꾸면 되므로 나중에 확장 가능하다.

### Redis 를 정본으로 (DB 아님)

모든 클릭이 읽는 값이다. DB 에 두면 클릭당 쿼리가 하나 붙고, 캐시를 씌우면 결국 Redis 를 읽게 되니
DB 를 정본으로 둘 이유가 없다. 차단이 필요한 상황은 대개 DB 가 힘들 때라는 점도 근거다.

### 가드로 판정 (미들웨어 아님)

`main.ts` 미들웨어에 붙이면 DI 밖이라 `CachePort` 를 `app.get()` 으로 꺼내야 한다.
가드로 두면 DI 가 깔끔하고 `modules/` 90% 커버리지 강제에도 맞는다.
실행 시점 차이(미들웨어 vs 가드)는 파이프 이전이라 실질 비용 차이가 없다.

### 로컬 캐시 3 초

클릭당 Redis 왕복을 없애기 위함이다. 대가는 반영 지연 최대 3 초.
이 코드베이스가 트래킹 응답에서 14 바이트 단위로 아끼고 있는 맥락(컨트롤러 주석)을 고려하면
클릭당 Redis 왕복 추가는 맞지 않는다고 판단했다.

### 어드민 컨트롤러를 기존 config 모듈에 넣지 않음

기존 `config` 모듈은 캠페인별 이벤트 매핑(`campaign_config`)이라 성격이 다르다.
전역 스위치를 끼워넣으면 `/config/:campaignId` 와 한 컨트롤러에 섞인다.
`tracking` 모듈 안에 별도 컨트롤러를 둔다.

## 주의 사항

- `/health` 는 절대 차단 대상에 넣지 않는다. ECS 가 NLB 타깃 그룹 헬스체크에 쓰므로
  막으면 태스크가 영구 unhealthy 로 교체를 반복한다.
- 어드민 컨트롤러는 트래킹 포트에 노출되지 않는다 — `main.ts` 의 `TRACKING_PUBLIC_PATHS` 가 막는다.
  이 정규식을 넓힐 때 `/tracking-mode` 가 새어 들어가지 않는지 확인할 것.

## 2026-09-07 — 프론트 화면

### 새 라우트가 아니라 developer 탭

`developer` 라우트가 이미 `PrivateRoute allow={['DEVELOPER']}` 로 감싸여 있어 권한이 그대로 맞는다.
새 라우트를 파면 메뉴 항목이 늘고 가드를 또 걸어야 하는데 얻는 게 없다.
기존 화면이 이미 Tabs 구조라 `트래킹 제어` 탭을 하나 더하는 것으로 끝났다.

### Radio + [적용] 2단계, 차단 방향만 확인 모달

세 상태가 동시에 보여야 긴급 상황에 헷갈리지 않아 Select 가 아니라 Radio 로 했다.
선택 즉시 저장하지 않고 [적용] 을 눌러야 하며, `half`·`closed` 로 가는 방향만 확인 모달을 띄운다.
`open` 으로 되돌리는 것은 안전한 방향이라 모달 없이 바로 적용한다 — 긴급 복구에 클릭을 하나 더 요구하지 않는다.
모달 여부는 `shared/lib/tracking-mode.ts` 의 `confirm` 플래그가 정한다.

### MSW 목을 추가하지 않음

`mocks/CLAUDE.md` 가 "backend 에 없는 엔드포인트만 목킹한다" 고 명시한다.
`/tracking-mode` 는 backend 에 구현돼 있으므로 목을 넣으면 실제 연동 확인이 막힌다.

### 테스트에서 걸린 것 두 가지

- antd `Modal.confirm` 은 title 을 `ant-modal-title` 과 `ant-modal-confirm-title` 두 요소에 렌더한다.
  단일 조회(`findByText`)가 "Found multiple elements" 로 실패하므로 `findAllByText` 를 쓴다.
  또 모달이 `document.body` 에 붙어 언마운트로 정리되지 않아 `afterEach` 에서 body 를 비운다.
- react-query 의 `mutate` 는 두 번째 인자로 컨텍스트(`{ client, meta, mutationKey }`)를 넘긴다.
  `toHaveBeenCalledWith('open')` 은 인자 개수가 달라 실패하므로 첫 인자만 확인한다.

### 커버리지

`vite.config.ts` 의 coverage include 는 순수 로직 파일만 나열한다(화면 컴포넌트는 antd·react-table 의존이라 제외).
새로 추가한 api 함수는 `/* v8 ignore */` 범위(axios 호출 구간) 안이라 임계에 영향이 없다.
패널 테스트는 커버리지가 아니라 동작 회귀를 막기 위해 작성했다.
