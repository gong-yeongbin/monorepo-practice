요청 경로와 VPC 구성

태스크 하나가 포트 두 개를 열고, ECS 서비스가 타깃 그룹 둘에 동시 등록된다. NLB는 L4라 경로를 못 보므로 앱이 진입 포트를 보고 공개 경로만 통과시킨다 — 3002에서는 /tracking, /*/install, /*/event, /health만 받고 나머지는 404다. 이게 없으면 어드민 API가 평문 80에 그대로 열린다.

왜 트래킹만 NLB인가

ALB의 LCU는 네 개 차원 중 최댓값 하나로만 과금되는데, 광고 클릭은 연결 재사용이 없는 일회성 요청이라 신규 연결 차원이 홀로 지배한다. 이 한 가지 성질이 LB 선택을 갈랐다.

한 호스트명의 A 레코드는 로드밸런서 하나만 가리킬 수 있어 "80은 NLB, 443은 ALB"가 성립하지 않는다. api.는 매체에 배포돼 바꿀 수 없으므로, 프론트만 쓰는 어드민 쪽을 admin-api.로 옮겼다 — 변경 비용은 VITE_API_URL 한 줄이다.

modules/frontend · envs/prod/storage.tf

정적 자산 — 버킷은 열지 않는다

프론트 번들과 광고 소재 모두 버킷은 완전 비공개로 두고 CloudFront OAC로만 읽는다. 광고 소재가 별도 서브도메인을 쓰는 이유는 업로드 시점의 절대 URL이 advertising.image 컬럼에 영구 저장되기 때문이다 — *.cloudfront.net을 쓰면 배포를 다시 만드는 순간 저장된 URL이 전부 깨진다.

단일 AZ — 무엇이 달라졌나

레거시는 WAS 4대와 RDS가 2a에 있는데 ElastiCache 두 노드만 2b·2c에 있었다. Redis Stream 기반이라 클릭마다의 XADD와 캠페인 캐시 조회가 전부 AZ를 넘었고, 양방향 과금이라 월 ~10.2TB의 캐시 트래픽이 23.3TB로 청구됐다. 4개월 내내 일관적이다.

Valkey 레플리카를 굳이 다른 AZ에 두지 않는 근거는 RDS가 Single-AZ라는 점이다. AZ 하나가 죽으면 어차피 서비스 전체가 멈추므로, 살아남지 못할 시나리오에 복제 전송료를 낼 이유가 없다. 노드 단위 장애에 대한 자동 페일오버는 그대로 유지된다 — multi_az_enabled만 끄고 automatic_failover_enabled는 켠 채로 둔다.

코드 구성

infra/terraform/
├── bootstrap/          state 버킷 생성 — 이 디렉토리만 로컬 state, 1회 apply
├── modules/
│   ├── network/          VPC · 서브넷 4 · 보안그룹 4 · primary_az_index
│   ├── database/         RDS + DATABASE_URL SSM 파라미터
│   ├── cache/            Valkey 복제 그룹 (같은 AZ 2노드)
│   ├── ecr/              backend 이미지 리포지토리
│   ├── acm/              ECDSA 인증서 + Route53 DNS 검증
│   ├── backend/          ALB · NLB · ECS · IAM · 오토스케일링 · JWT SSM
│   └── frontend/         S3 + CloudFront OAC
└── envs/prod/          모듈 배선 · Route53 · SES · 앱 버킷 · 소재 CDN

보안그룹은 순환 참조를 피하려 전부 network에서 만들고 ID만 넘긴다. 체인은 alb(80,443) → app(3001) / nlb(80) → app(3002) → rds(5432) · redis(6379)다. DB 비밀번호와 JWT 시크릿은 Terraform이 생성해 SSM SecureString에만 기록하므로 tfvars에 비밀이 없고, 앱은 task role을 쓰므로 정적 AWS 키가 필요 없다.

현재 위치

배포 순서

  1. ✓AWS CLI 설치 · 자격증명 설정 — 공식 pkg (brew 버전은 python 링크 문제로 깨짐)
  2. ✓Cost Explorer로 DT $865 구성 실측 — AZ 간 $233 규명, 단일 AZ로 반영 완료
  3. →bootstrap apply → backend.tf에 버킷명 기입 — 리소스는 S3 버킷 하나, 레거시 무영향
  4. ·envs/prod plan → apply — desired_count 0, cutover_dns_enabled false라 레거시 트래픽 그대로
  5. ·Dockerfile 작성 → ECR push — pnpm workspace · arm64 필수
  6. ·autoscaling 활성화 후 재-apply — NLB·ALB 도메인으로 직접 검증
  7. ·앱 수정 · 프론트 배포 — CORS, 302 슬림화, 트래킹 로그 억제
  8. ·마스터 이관 → DNS 컷오버 — cutover_dns_enabled true가 곧 전환

주의 하나. 트래킹 경로에서 클릭당 CloudWatch 로그가 한 줄이라도 남으면 하루 20GB, 월 $400+가 붙는다. 이건 Terraform이 아니라 앱에서 막아야 한다.

구성도는 infra/terraform의 현재 코드 기준이며 fmt -check·validate를 통과한 상태다. 아직 apply 전이므로 실제 생성된 리소스는 없다.
